# Axiom Protocol — Sui Phase 8 Authorization Model

**Module:** `axiom::claim_campaign`, `axiom::guarded_treasury`
**Date:** 2026-05-16
**Status:** Operational Reference

---

## Authorization Architecture

The Axiom Sui Phase 8 authorization model uses Move's object capability (ocap) pattern. Authority flows entirely through possession of unique Sui objects — not through caller address checks or role mappings. This document describes each capability, its scope, and the multi-party requirements for exercising it.

## Capability Binding Invariants

**AdminCap binding:**
```move
assert!(cap.campaign_id == object::id(campaign), E_WRONG_CAMPAIGN);
```
Every admin function on `ClaimCampaign` checks this. A cap from campaign A cannot authorize any operation on campaign B.

**TreasuryOperatorCap binding:**
```move
assert!(cap.treasury_id == object::id(treasury), E_CAP_MISMATCH);
```
Every operation on `GuardedTreasury` checks this. A cap from treasury A cannot operate on treasury B.

**Package-internal access:**
```move
public(package) fun take_balance<T>(...): Balance<T>
```
`take_balance` is restricted to the `axiom` package. External contracts cannot call it even if they hold a treasury reference.

## Multi-Party Authorization Configuration

Phase 8 does not deploy a native Sui multisig contract — it relies on Sui's built-in `multisig` key type for the operator address. The recommended configuration:

| Parameter | Value |
|-----------|-------|
| Scheme | Sui native multisig |
| Threshold | 2-of-3 |
| Signers | Axiom core team (3 hardware wallets) |
| Scope | Holds AdminCap + TreasuryOperatorCap |

**Creating a Sui multisig address:**
```bash
sui keytool multi-sig-address \
  --pks <PK1> <PK2> <PK3> \
  --weights 1 1 1 \
  --threshold 2
```

**Signing a multisig transaction:**
```bash
# Each signer signs the serialized transaction bytes
sui keytool sign --address <SIGNER_ADDRESS> --data <TX_BYTES>

# Combine signatures
sui keytool multi-sig-combine-partial-sig \
  --pks <PK1> <PK2> <PK3> \
  --weights 1 1 1 \
  --threshold 2 \
  --sigs <SIG1> <SIG2>
```

## Claimant Authorization Flow

A claimant proves eligibility via a Merkle inclusion proof generated by the TypeScript toolchain:

```
Eligibility CSV → buildMerkleTree.ts → MerkleTree { root, leaves, layers }
                                            │
                                            ├── root → stored in ClaimCampaign.merkle_root
                                            │
                                            └── generateProof.ts → ProofResult { proof, root, leaf }
                                                                         │
                                                                         └── serializeProof.ts → bytes[] for PTB
```

On-chain verification (`merkle::verify`):
```
leaf = keccak256(addr_32_be ++ amount_8_le)
current = leaf
for each sibling in proof:
    current = keccak256(sort_lex(current, sibling) ++ sort_lex_second(current, sibling))
return current == campaign.merkle_root
```

**Authorization invariants enforced on-chain:**
1. Leaf encodes the exact (sender_address, amount) pair — cannot be forged for a different address
2. Proof depth bounded at 32 (A1) — griefing resistance
3. Amount must exactly equal `campaign.amount_per_claim` — no partial or over-claims
4. Campaign must be active and not expired — temporal gating

## API Layer Authorization

The TypeScript API layer (`pages/api/sui/`) is read-only and does not hold any on-chain authority:

| Route | Method | Auth Required | Scope |
|-------|--------|--------------|-------|
| `/api/sui/campaigns` | GET | None | Read campaign list |
| `/api/sui/campaigns/[id]` | GET | None | Read campaign state |
| `/api/sui/eligibility` | GET/POST | None | Compute proof (client-side) |
| `/api/sui/claim-status` | GET | None | Check if address has claimed |

All write operations (fund, activate, pause, close, claim) must be performed via signed Programmable Transaction Blocks (PTBs) from the wallet holder. The API backend never holds or transmits private keys.

## Operator Dashboard Authorization

The operator dashboard at `/operator/chains/sui-phase8` is protected by the standard Axiom operator cookie (`requireOperatorCookie`). It provides:

- Campaign list with live on-chain state
- Eligibility CSV upload and Merkle root computation (TypeScript local verification)
- Campaign creation parameters preview (does not submit transactions)

Actual campaign transactions are submitted by the operator's wallet (Sui wallet browser extension), not by the backend.

## Event-Based Audit Trail

All authorization decisions that result in state changes emit on-chain events:

| Event | Fields | Use |
|-------|--------|-----|
| `CampaignCreated` | campaign_id, admin_cap_id, creator | Detect unauthorized campaign creation |
| `CampaignFunded` | campaign_id, amount, new_balance | Treasury audit |
| `CampaignActivated` | campaign_id, epoch | Activation record |
| `CampaignPaused` | campaign_id, epoch | Incident log |
| `CampaignClosed` | campaign_id, total_claims, total_paid | Final accounting |
| `ClaimMade` | campaign_id, claimant, amount, remaining_pool | Individual claim audit |
| `TreasuryCreated` | treasury_id, operator_cap_id | Cap issuance record |
| `TreasuryDeposit` | treasury_id, amount, new_balance | Inflow audit |
| `TreasuryWithdrawal` | treasury_id, amount, recipient | Outflow audit |

Events are indexed by the campaign_id field, enabling O(1) lookup of all events for a given campaign from a Sui full node.
